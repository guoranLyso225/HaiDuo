# 编辑、撤销与纠错设计方案

日期：2026-11-17。状态：部分实现，当前范围见下方实施增量。依据当前SKU列表、整单库存事务及不可变利润确认模型。

实施增量：SKU名称/当前成本编辑及审批、成员职级配置已实现，范围与限制见[SKU审批手册](SKU_APPROVALS.md)。本方案其余规则仍是后续设计，尤其通用业务审批和提权双人审批未实现。

## 交互原则

- 保存前：表单取消不写入，关闭有改动的表单时提示放弃或继续编辑。
- 保存后：名称等基础资料可编辑；库存、履约、财务通过有业务含义的反向操作纠错，不删除历史记录。
- 成功提示写清结果和下一步。只有后端确实支持安全逆操作时才显示撤销按钮；按钮超时不意味着审计记录消失。
- 多字段操作用一个居中表单；详细历史用抽屉。危险操作说明影响范围、原因、权限和不可执行的理由。
- 修改携带版本号，过期版本返回409并提示刷新核对；不能静默覆盖其他员工的修改。撤销同样检查当前版本及下游依赖。

## 分模块规则

| 对象 | 新增操作 | 限制及历史策略 |
|---|---|---|
| 商品/SPU | 编辑商品名称、图片；归档/恢复 | 图片明确标注同商品所有SKU共用；归档保留订单、库存和文件引用 |
| SKU | 单独编辑规格名、编码、当前采购成本；停用/启用 | UUID身份不变。编码修改需查重并更新当前企业外部映射/别名；旧编码保留别名且不可分配给其他SKU，导入命中别名明确提示。停用SKU禁止新导入、新预占，允许已有预占履约和取消 |
| SKU成本 | 保存新成本，展示生效范围 | 只影响后续新订单；历史成本快照不变。运营不编辑成本，财务/管理员编辑，防止借编辑入口扩大权限 |
| 店铺/仓库 | 编辑名称、停用、恢复 | 店铺订单目前以名称关联，必须先迁移到store_id外键后开放店铺改名，不能只改显示表。仓库按ID关联，可改名；有预占/待履约/同步绑定时禁止停用 |
| CSV导入 | 预检查、预览、错误行、批次历史、撤销批次 | 先解析校验，再事务提交。仅CSV来源且全部仍NEW、无费用/预占/发货/确认/后续修改时允许整批撤销；保留批次及撤销记录。平台来源不允许用此入口撤销 |
| NEW订单 | 编辑SKU数量、履约仓库、备注 | 仅CSV/手工来源可改业务行；重算成本需单独确认新快照并留历史。平台权威字段只读，提供重新同步。收入/汇率修正由管理员/财务处理，保留旧版本 |
| RESERVED订单 | 释放预占并返回NEW；取消订单 | 释放与取消不同：释放可重新编辑，取消为终态。多SKU一次事务全部释放；重复请求不重复增可用库存 |
| CANCELLED订单 | 复制为新订单 | 首版不直接复活旧单，复制仅用于CSV/手工来源并使用新编号；平台取消依权威状态核对 |
| 入库 | 更正入库、冲销入库 | 原流水保留，生成反向流水并引用原入库。仅该仓可用库存足够扣回且无相关后续业务影响时允许；否则采用盘点调整，不伪造撤销 |
| 库存 | 盘点调整、调拨（后续） | 不直接编辑现存/预占字段。输入实盘数量、原因及凭证；不得使现存小于预占。调拨须同事务记录双向流水 |
| SHIPPED订单 | 更正运单；发货纠错申请（后续） | 更正承运商/运单保留旧值，不自动加库存。未交运的误发货需单独流程；已交运或已签收使用退货验收入库。首轮不实现一键撤销发货 |
| 费用 | 修改费用并查看版本/差异 | 替换类别金额须明确显示前后值，保留费用版本；已有实际确认显示需重新核对，不改写旧确认 |
| 实际贡献确认 | 新建调整版本、关联原版本 | 旧记录不可修改/删除，保持现有数据库不可变约束。展示当前有效版本、历史版本与调整原因 |
| AI草稿/知识资料 | 编辑草稿、审核、归档；知识更新/删除及索引同步 | 草稿不自动发布。资料更新导致重新切分索引，来源引用绑定文档版本；删除跨租户不可见，失败可重试 |

## SKU编辑示例

商品每行增加“编辑SKU”和“更多”。点击后单窗显示所属商品（只读）、SKU编码、SKU名称、采购成本及权限提示。编码改动展示“旧编码将保留为导入别名”；成本改动展示“现有订单成本与利润保持历史快照”。提交前展示变更摘要。

例：DEMO-BAG名称改为旅行包、当前成本200改为220：新订单使用220；既有100USD示例仍按200计算398贡献。运营可改名称，成本字段只读。已停用SKU有状态标签，可在筛选中显示，库存和历史订单仍可查看。

第一轮可先开放名称/成本编辑，编码在别名及平台映射规则实现前保持只读，不能为了“可编辑”破坏CSV和平台同步。

## 权限和可靠性

所有接口由当前认证成员关系确定租户。管理员负责基础资料、停用恢复和纠错；运营编辑商品非财务属性、处理未履约订单；仓库执行入库/释放/盘点，冲销限管理员或经明确授权的仓库角色；财务修改成本、费用及实际确认。最终按现有权限表逐接口补充细分权限，不仅隐藏按钮。

业务变更、审计和Outbox同事务；事务内校验关联数据、状态和版本。冲销、释放、批次撤销需幂等键及唯一约束；增加changed_by、原因、旧值/新值、关联原操作。列表、搜索、缓存与别名检索保持企业范围。禁止硬删被业务引用对象。

## 分批落地与验收

### 新增前置规则：分级审批（2026-11-17）

本节覆盖前文直接保存规则：需要审批的变更，保存只创建申请，审批通过并成功执行后才改变业务数据。以下是设计，当前系统四类角色尚未实现职级与审批功能。

**职责与职级分别建模。** ADMIN/OPERATIONS/WAREHOUSE/FINANCE表示能处理哪个业务领域；成员另有职级，不把财务、仓库、运营简单排成上下级。职级由企业管理员分配，禁止自行提升。

| 等级 | 定位 | 生效规则与审批权 |
|---|---|---|
| L1 TRAINEE | 实习/受训人员 | 获授权范围内的所有业务写入均提交审批，不直接生效；不能审批 |
| L2 STAFF | 正式员工 | 日常低风险操作可直接执行；关键变更须主管审批；不能审批他人 |
| L3 SUPERVISOR | 业务主管 | 在职责范围内审批L1/L2申请；关键变更本人提交时须另一位合格主管或管理员审批 |
| L4 ADMIN | 企业管理员 | 管理成员与权限、跨职责审批；关键变更依然禁止自审，需另一企业管理员审批 |

管理员拥有企业范围最高权限，不跨越租户。兼任多个职责必须显式授权。审批者需职级严格高于申请者且拥有相应业务权限；L3关键变更是明确例外，允许另一位同级、同职责主管审批；L4关键变更允许另一位同级管理员审批。所有例外仍禁止同一账号自审。

**审批矩阵：**

| 变更类别 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| 商品名称/图片、内部备注、AI草稿编辑 | 提交同职责主管或管理员审批 | 职责授权内直接执行 | 职责授权内直接执行 | 直接执行 |
| 新建商品、普通入库、订单导入/行编辑、预占/释放、发货、运单更正 | 提交同职责主管或管理员审批 | 职责授权内直接执行 | 职责授权内直接执行 | 直接执行 |
| SKU成本/编码、订单金额/汇率、费用修改、实际贡献确认 | 提交财务主管或管理员审批；无财务职责不得提交 | 财务主管或管理员审批 | 另一财务主管或管理员审批 | 另一管理员审批 |
| 入库冲销、盘点减少、批次撤销、订单取消、停用归档、误发货纠错 | 提交对应主管或管理员审批 | 对应主管或管理员审批 | 另一对应主管或管理员审批 | 另一管理员审批 |
| 成员、职级、权限、连接凭据配置及安全设置 | 不可提交或执行 | 不可提交或执行 | 可提出成员调整申请，无权生效 | 普通成员创建可直接；提权、管理员变更及安全配置须另一管理员审批 |

L1申请由L3/L4审批，不由L2审批。读取、筛选、导出（有原权限）、本地表单取消与退出登录不走审批。审批不能扩大申请者业务权限，例如仓库实习生不能申请修改采购成本。密码重置需独立受控流程，不在通用申请正文保存密码或令牌。

**申请流程与界面：**

1. 原“保存/确认”按当前权限改为“提交审批”。弹窗显示审批人范围、变更前后对比、影响对象及申请原因；提交后提示“已提交，尚未生效”。
2. 增加“审批中心”，包含我的申请、待我审批、已处理。详情展示申请人、职责/等级、提交时间、变更摘要、状态、审批意见及执行结果。首页显示待办数量，不向聊天/邮件自动发送通知。
3. 状态为DRAFT、PENDING、REJECTED、WITHDRAWN、EXPIRED、STALE、APPLIED、APPLY_FAILED。审批通过与业务变更在同一数据库事务内完成；只有成功提交才显示APPLIED。已审批的业务拒绝或系统失败不可伪装为成功。
4. 申请待处理默认24小时到期；提交不会预先修改库存或占用库存。审批时重新校验库存、订单状态、对象版本、审批者/申请者当前成员关系及权限。版本变化标STALE，展示差异，申请者重新提交，不能覆盖新数据。
5. PENDING期间申请人可撤回，不等于撤销已生效业务。驳回必须填写原因。修改申请内容生成新版本并使旧申请失效，不能在审批人看过后偷偷替换载荷。
6. 审批接口需CSRF、幂等键、申请行锁、预期状态/版本及唯一执行约束；审批操作与业务审计、Outbox同事务，重复点击或消息重复不能执行两次。执行失败回滚业务写入，失败原因用独立受控事务记录。
7. 原写接口也必须调用统一授权/审批策略，禁止绕过页面直接请求REST生效。审批只能执行白名单类型的业务命令，不能传任意SQL、URL或反射方法；JSON中不保存密钥和完整客户地址。

**已生效操作的撤销**也是新业务操作：按其类别重新决定是否审批。举例：L1入库申请经主管批准后，L1发现数量错误，须提交冲销申请；不得通过“撤销”绕过审批直接扣库存。

**人员不足与初始化：** 只有一位管理员时，关键变更明确显示“缺少独立审批人”，不自动降级为自审。企业首次管理员通过受控初始化创建，不经通用提权审批；后续必须建立第二位管理员或相应主管。现有成员升级时不自动把所有ADMIN变成可绕过审批的超级账号；本地demo需准备两个不同审批账号演示。固定admin/1234不豁免自审限制。

**验收新增：** L1提交后商品/库存不变；主管批准后恰好执行一次；自审/越级/错职责/跨企业审批拒绝；审批前对象变化或库存被占用不能覆盖；撤回与批准并发仅一个成功；角色撤销后不得批准或继续执行旧申请；失败事务不产生库存、费用或Outbox副作用。审批中心需覆盖手机、无审批人、过期、执行失败、驳回再提交等状态。

分级审批应与第一批基础编辑共同落地，后续撤销/冲销接口复用同一策略，不能先开放写入再补审批。

1. **优先一：基础编辑与反馈**。编辑SKU名称/当前成本（编码暂只读）、更换商品图片、仓库改名、费用差异确认、未保存退出提醒、统一操作结果。验证成本编辑不改398历史结果，越权/跨企业拒绝，旧版本提交409。
2. **优先二：安全撤回**。释放预占、入库冲销、CSV预览及批次撤销。真实PG测试多SKU全量回滚、重复十次无副作用、并发冲销与预占库存不为负；下游状态变化时撤销明确失败。
3. **优先三：历史整理**。停用归档/恢复、SKU编码别名、store_id迁移后店铺改名、操作历史入口。归档不影响历史报表，默认选择器排除停用对象，历史详情仍能解析。
4. **后续独立流程**。退货、调拨、误发货纠错、知识版本维护。需单独产品规则，不能伪装成简单撤销。

每批更新使用手册和实施记录，前端表单/角色/异常重试用浏览器验收，库存及财务约束用真实PostgreSQL集成测试。设计文档不计作功能完成。

实施第二批：释放预占与整笔入库冲销已独立审批落地，库存轮次、反向流水及审批时校验已实现，见INVENTORY_CORRECTIONS.md。部分冲销、实物退货、盘点、CSV批次预览/撤销、通用审批仍未实现。

实施第三批：CSV逐行预览、确认导入、批次追溯及全批无后续业务时独立逻辑撤销已实现，见CSV_IMPORT_BATCHES.md。不永久删除、不撤销重复旧单、不自动复活原订单号；其他通用审批/归档/退货等仍未实现。


## 普通入库职级审批（2026-11-18）

已接入原入库接口：L1仓库员工提交后等待独立仓库主管或管理员批准，批准前库存不变；L2及以上按原职责直接入库。V27 receipt_approval 按企业和请求键唯一，固定申请人和入库参数，重复请求不重复增加库存。系统设置的审批中心新增普通入库审批列表，支持批准、驳回、撤回和24小时过期。详细操作、接口及边界见 [普通入库审批](RECEIPT_APPROVALS.md)。其他普通业务写入尚未全面接入职级审批。


## 第五批：业务审批与详细纠错（2026-11-18）

普通业务L1审批、商品资料/编码/归档、订单行编辑及复制、盘点/部分冲销/实物退货、运单更正和成员提级/角色独立审批已编写并专项验收。使用步骤、V28/V29模型、接口、状态与范围以 [业务审批与详细纠错](BUSINESS_WORKFLOWS.md) 为准；较早章节“尚未接入”的说明为历史。待审CSV会保存指定模板载荷，不含客户地址；实物退货不自动退款或改变历史财务确认。完整验收结果见实施记录末尾。
